| D-005 | 2026-09-13 | The mandate does not bind a specific execution hash at signing time. The policy engine authorizes a specific execution (identified by `executionHash`) by verifying every material field against mandate constraints individually. The authorized hash is returned in `PolicyDecision` and must be used as the idempotency key. Any mutation to the intent produces a different hash, which has not been authorized. | The exact execution payload (calldata, minOutput) is known only at trigger time. Binding constraints individually is equivalent in security to hash commitment because every material field is constrained. | Accepted. See `src/domain/policy.ts`. |
| D-006 | 2026-09-13 | viem cryptographic utilities (`getAddress`, `isAddress`, `encodeAbiParameters`, `keccak256`, `hashTypedData`, `recoverTypedDataAddress`) are permitted in the domain layer. | These are pure functions: no network, no file system, no global mutable state. The architecture rule bans vendor service SDKs (The Graph, Privy, Uniswap, Anthropic), not cryptographic utilities. Domain tests need no network. | Accepted. |
| D-007 | 2026-09-13 | No deployed verifying contract for EIP-712 in the ETHOnline 2026 demo. Signature verification is off-chain: recover signer from EIP-712 hash, compare to `mandate.owner`. The `verifyingContract` field is absent from the domain separator. **Corrected risk analysis (Phase 2 security review):** (1) Knowing an owner address does NOT enable signature forgery — ECDSA prevents that. (2) The real risks are weaker deployment-level domain separation (two ExitLane deployments on the same chain share the same separator) and cross-application replay (any app with the same domain name/version/chainId could replay a mandate). (3) Separately: the API layer must verify that `mandate.owner` is the wallet address of the authenticated Privy user; without this check an attacker who knows an operator's address could submit mandates on their behalf (but cannot forge the signature). | Deploying a verifying contract is out of scope for a seven-hour build. Off-chain recovery is sound when the API layer enforces Privy ownership. | POC only. Add `verifyingContract` and Privy ownership check before production. See `src/domain/mandate.ts` module docstring. |
| D-008 | 2026-09-13 | `tsconfig.json` target raised from `ES2017` to `ES2020`. | BigInt literals (`1n`, `0n`) require `target ≥ ES2020`. Node ≥22 supports ES2020 natively. The project's `engines` field already requires Node ≥22. | Accepted. |
| D-009 | 2026-09-13 | `approvedChainId` in `ExitMandateSchema` uses `SafeChainIdSchema` instead of `Uint256StringSchema`. This validates the value is a positive decimal integer ≤ `Number.MAX_SAFE_INTEGER` (9 007 199 254 740 991). Viem's `TypedDataDomain.chainId` requires a JS `number`; arbitrary uint256 values cannot be converted to `number` without loss. All real Ethereum chain IDs are far below this bound; the restriction is not a practical constraint. A chain ID above the bound is rejected at schema validation — it never reaches `hashMandate()`. | The previous `Number(mandate.approvedChainId)` conversion was unsafe for large bigints. The alternatives were: (a) constrain to a safe integer before conversion (this decision) or (b) patch viem's type to accept bigint (requires vendored types and a future API risk). Option (a) is simpler and sufficient for all real networks. | Accepted. See `src/domain/primitives.ts SafeChainIdSchema`. |
| D-010 | 2026-09-13 | Introduced `AuthorizationEnvelope` in `policy.ts`. The envelope binds `policyVersion`, `mandateHash`, `evidenceHash`, `executionHash`, `evaluatedAtMs`, and `outcome` into a single canonical struct hashed with `keccak256(abi.encode(...))`. It is computed by the policy engine and returned in every `PolicyDecision` (AUTHORIZED or BLOCKED). It is NOT user-signed. The `executionHash` within the envelope is the trusted value: the API layer must store the envelope server-side and recompute `hashExecutionIntent(actualIntent)` immediately before execution, requiring exact equality. An attacker who recomputes a hash for mutated calldata produces a different hash than the stored trusted value and is still blocked. | The prior design exposed a trust-boundary gap: `proposedExecutionHash` could be supplied by the browser, allowing an attacker to mutate calldata and recompute a matching hash. The rename to `trustedExecutionHash` in `PolicyInput` documents that the API layer must never accept this value from an untrusted caller. | Accepted. See `src/domain/policy.ts AuthorizationEnvelope`. |
